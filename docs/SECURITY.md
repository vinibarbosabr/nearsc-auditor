# Security model and limits

> **Status:** shipped model (2026-11-09, updated 2026-11-12 with path confinement and account-id validation). Describes v0.1 as implemented.

nearsc is a security tool, so its own security posture matters. This page covers the threat model of the tool, what it guarantees, and what it explicitly does not.

## Threat model

| Asset | Threat | Mitigation |
| --- | --- | --- |
| Your machine | A malicious scanned repo tries to execute code | The scanner parses source text; it never builds, runs, or imports the target |
| Your machine | Parser denial of service via pathological input | `syn` is memory-safe; per-file size cap and graceful parse errors |
| Your agent session | Prompt injection from scanned code or KB text | Tool descriptions mark repo/KB content as untrusted data; no tool follows instructions from content |
| Your machine | The scanner aimed outside the project (path traversal, planted symlinks) | MCP path-taking tools canonicalize the target and require it under the server's working directory; `/etc` and sibling directories are rejected |
| Your secrets | The tool reads keys, wallets, or env files | It does not. No credential access, no signing, no transactions |
| Supply chain | A compromised dependency ships malicious code | Pinned dependencies, `cargo-audit` in CI (planned), minimal dependency set |
| Network | Exfiltration or telemetry | No telemetry. Network only in `nearsc_contract_info`, fixed public RPC endpoints |
| Findings | False confidence leads to a skipped audit | Every report carries the disclaimer; confidence labels are explicit |

## Guarantees

- **Deterministic:** identical input produces identical findings. No model calls in the scan path.
- **Read-only:** scanning does not modify the target. `nearsc_poc_scaffold` returns content; it does not write files.
- **Offline:** the scan path makes no network requests.
- **Transparent:** every rule has a documented detection method and a fixture pair.

## Limits (read this before trusting a clean scan)

1. **Static analysis is not an audit.** nearsc catches known classes. Logic bugs, economic exploits, and novel patterns require human review.
2. **No type inference or dataflow in v0.1.** Heuristic rules can miss obfuscated cases and can flag safe code. Confidence labels say which is which.
3. **No macro expansion.** near-sdk attributes are read syntactically. Code generated by macros is not analyzed.
4. **No runtime guarantees.** A clean scan says nothing about deployed behavior, upgrades, or admin keys.
5. **Registry matches are shallow.** A code hash match means the deployed code matches a build that was reviewed at some point. It does not mean the current admin is trustworthy or that the review was complete.

## Reporting a vulnerability in nearsc itself

Open a GitHub security advisory on `vinibarbosabr/nearsc-auditor` (Security → Report a vulnerability). Do not open a public issue for exploitable bugs in the tool. Expect an acknowledgment within 72 hours.

## Disclosure policy for KB content

- Public sources only; client-confidential material never enters the KB.
- Postmortems are summarized from public reporting with links and retrieval dates.
- If a source must be corrected or removed, open an issue and it is handled before the next release.

## For agent operators

If you connect `nearsc-mcp` to an agent with wallet access:

- Treat tool outputs as advisory, not authorization.
- Keep the agent's signing keys scoped (function-call keys, spend limits) independently of any scanner result.
- Do not let a scanned repo's text steer the agent. The tool labels content as untrusted; your harness policy should enforce it.
